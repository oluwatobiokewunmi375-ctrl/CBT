## Summary
The Super Admin surface is present and mostly implemented. Key pages, APIs, seeds, and tests exist. There are minor inconsistencies and a few security/practical risks to address before completing Phase 2.

## Files & Entry Points Reviewed
- `app/super-admin/page.jsx` — Super Admin landing page.
- `app/super-admin/dashboard/page.jsx` — Dashboard server component (counts and cards).
- `lib/auth/session.js` — session role redirects (contains super-admin redirect to `/super-admin/dashboard`).
- `lib/auth/roles.js` — role mappings (maps `SUPER_ADMIN` to `super_admin`).
- `lib/auth/redirect.js` — role->path redirects (contains `if (role === "super_admin") return "/admin/dashboard"` — likely incorrect).
- `app/api/admin/super-admin/route.ts` — API to create initial SUPER_ADMIN (protected by setup key).
- `app/api/school/route.ts` — checks for `decoded.role !== "SUPER_ADMIN"` in spots.
- `app/api/admin/*` — many admin APIs guard with role checks including `SUPER_ADMIN`.
- `scripts/create-mock-accounts.ts`, `lib/seedExam.ts` — seed/scripting that creates SUPER_ADMIN accounts.
- Tests: `tests-e2e/*` and `__tests__/*` reference `superadmin@test.com / admin123`.
- Playwright traces contain test credentials and bearer tokens (sensitive data) under `playwright-traces/`.

## Findings (issues, inconsistencies, and risks)
1. Redirect inconsistency: `lib/auth/roles.js` normalizes `SUPER_ADMIN` -> `super_admin`, but `lib/auth/redirect.js` maps `role === "super_admin"` to `/admin/dashboard` which will route super admins to the wrong dashboard. This can cause wrong redirects and access issues.
2. Role string mixing: code occasionally checks `decoded.role` against `SUPER_ADMIN` (uppercase) and other places against `"super_admin"` (snake_case). Normalize and document canonical role enum.
3. Playwright traces and other resource files contain plaintext credentials and JWTs; these are security-sensitive and should be removed from repository or excluded from CI artifacts.
4. Many API routes correctly guard using role checks, but a quick pass should confirm middleware is applied uniformly and that client-side pages also enforce server-side checks to avoid UI leakage.
5. Seed scripts create SUPER_ADMIN accounts (good), but multiple seeds and test accounts with differing passwords/emails may cause confusion in environments. Consolidate recommended test credential docs.
6. Potential redirect/loop risks: verify middleware and client code do not cause redirect loops for unauthorized users (e.g., role mismatch between token and redirect logic).
7. Hydration/SSR mismatch risk: some admin pages are client components; ensure server-side data fetching for `app/super-admin/dashboard` is consistent (it appears to use server-side Prisma counts — good).
8. Missing explicit CSRF protections on mutating admin APIs — ensure actions are CSRF-safe (Next.js route handlers and server-side checks help but confirm forms/clients include proper tokens if needed).

## Severity & Priority
- High: Redirect inconsistency (can break access), plaintext credentials in traces (security leak).
- Medium: Role string normalization, CSRF confirmation, middleware uniformity.
- Low: Seed account consolidation, UI polish items (Phase 3).
